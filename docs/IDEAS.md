# Идеи на будущее

То, что сознательно не входит в v1 (см. [SPEC.md](SPEC.md)), но должно влиять на архитектуру уже сейчас.
Таблица «к чему вернуться» по вопросам v1 — в SPEC.md, раздел 6.

## ⚠️ Не забыть
- **Поиск файлов по именам колонок в Spotlight** (SPEC §1.3, Q16). Современное расширение
  `CSImportExtension` (`Spotlight/`) написано, но система его не вызывает при индексации, а при ручном
  вызове песочница прячет файл. Варианты: классический `.mdimporter` со своим разбором footer (Thrift,
  без DuckDB), или повторить с Developer ID — возможно, мешает ad-hoc подпись.
- **Папки и партиционированные датасеты** (`*.parquet`, hive-партиции `year=2024/…`) как одна таблица.
  Engine и именование таблиц не должны предполагать, что «таблица = один файл».

## Дизайн-проход (после функционала)
Сейчас всё на стандартных компонентах AppKit. Что переделать, когда функционал устоится:
- Строка фильтров в шапке грида: сейчас это обычные поисковые поля под заголовками, выглядит грубо.
  Варианты: компактные поля без рамки, иконка-воронка в заголовке, подсветка колонок с активным фильтром.
- Иконка приложения.

## Бэклог после сравнения с Parkour и DuckDB UI (2026-10-21)

Решения по итогам разбора [Parkour](https://matt.sh/parkour) 0.2.0 и DuckDB UI.

**Делаем**
- **Размер текста в гриде**: View → Bigger / Smaller / Actual Size (⌘+ / ⌘− / ⌘0), как в нативных
  приложениях. Без кнопок масштаба в тулбаре.
- **Пробел / ⇧Пробел** в гриде — страница вниз / вверх.
- **Сжатые файлы**: `.csv.gz`, `.tsv.gz`, `.json.gz`, `.jsonl.gz`, `.zst` — DuckDB читает сам, нужно
  зарегистрировать типы файлов.
- **Мини-статистика в предпросмотре** таблицы из панели «Tables» (пробел): тип, % NULL, число уникальных,
  min / max — коротко, не полная вкладка Stats.
- **Базы SQLite и DuckDB** (таблицы базы как таблицы в запросах и просмотре) и **папки / партиционированные
  датасеты** как одна таблица (см. «Не забыть»).
- **Кнопки Open и Export в тулбаре** окна файла (как у Parkour). Кнопок масштаба и «назад / вперёд» не
  нужно.
- **Инспектор Parquet** — низкий приоритет: row groups, сжатие и кодировки по колонкам, статистика из
  footer, key-value метаданные (`parquet_metadata`). Возможно, третья вкладка рядом с Data и Stats.

**Нужно, но сначала подсмотреть реализацию**
- **Фильтр-выражение**: одна строка над гридом (`amount > 500 and city = 'Moscow'`) в дополнение к
  фильтрам по колонкам. У Parkour это поле «filter — SQL». Перед реализацией посмотреть, как сделано в
  других инструментах (DBeaver, TablePlus, DataGrip, Tad), — подсказки, автодополнение колонок, ошибки.

**Отложено**
- ⌘/ (закомментировать строки) — вместе с общей доработкой SQL-редактора, сейчас он сырой.

**Не делаем**
- Перестановка / скрытие колонок в гриде — вид должен показывать файл как есть.
- ✓/✗ для булевых и «·» вместо NULL — значения должны читаться однозначно, без угадывания.
- Instant SQL (результат по мере набора).
- Кнопки масштаба и «назад / вперёд» в тулбаре.

## Рабочее пространство
- ~~Вкладки~~ — сделано системными вкладками macOS (v0.1.2): файлы открываются вкладками одного окна,
  вкладку можно вынести в окно и обратно (Window → Merge All Windows). Собственные вкладки в стиле браузера
  не делаем: они дублируют систему.
- ~~SQL по нескольким файлам~~ — сделано (0.1.5): панель «Tables» в SQL-вкладке, файлы добавляются ＋ или
  перетаскиванием на панель / редактор как `t2`, `t3`… и под своим именем. Добавленные таблицы живут, пока
  открыто окно (сохранять между запусками — вместе с сохранёнными запросами).
- **Сохранённые запросы**: библиотека запросов с именами, привязка к файлу или к набору файлов.
- **Пользовательские шаблоны**: свои шаблоны с плейсхолдерами вдобавок к встроенным из v1.
- История запросов между сессиями, последний запрос для файла, поиск по истории.
- Восстановление сессии (открытые файлы, запросы, позиции скролла).

## Просмотр
- Вложенные типы: инспектор значения, разворачивание `STRUCT` в колонки, просмотр `LIST`/`MAP`.
- Фильтры по типам: диапазоны для чисел и дат, `=`, `IS NULL`, поповер со списком значений, строка `WHERE`.
- Multi-sort (Shift+клик).
- Форматирование: таймзона для `TIMESTAMP`, разделители тысяч, точность float.
- Связь грида и SQL: показывать фильтры и сортировку как SQL-запрос, открывать текущий вид в SQL-редакторе.

## Данные
- Сетевые источники: S3, GCS, HTTP(S) (через DuckDB `httpfs`).
- Другие форматы: CSV, JSON/NDJSON, Arrow/Feather, Excel, Iceberg/Delta.
- Экспорт текущего вида и результатов SQL в CSV/Parquet/JSON, копирование как Markdown/SQL `INSERT`.

## Архитектурные следствия для v1
- `Engine` должен изначально уметь регистрировать N таблиц, а не «один файл = одно соединение».
- Именование таблиц, алиасы `tN` и разрешение коллизий (`sales`, `sales_2`) вынести в отдельную функцию.
- Грид не должен знать, откуда пришли данные (файл, фильтр или SQL-результат): у него один протокол
  «источник страниц».
- Фильтр — отдельная модель (колонка + условие), а не просто строка: тогда потом добавятся условия по
  типам и перевод в SQL.
